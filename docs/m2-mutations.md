# M2.5 event mutations and replay

The project ledger is the source of truth. Opening or registering a project verifies its chain and checkpoints, then replays one `engagement.created` genesis and all recognized events. Version 1 creation metadata receives the deterministic M2.4 defaults. Unknown event versions, duplicate creation, foreign engagement IDs, missing scope objects, and inconsistent lifecycle snapshots make the project unavailable. Registration compares the current projection with the verified replay and repairs `project.toml` from that view.

The `ProjectMutationService` accepts an explicit owned project, expected ledger revision, UUIDv7 operation ID, method, route, and domain command. It serializes writes by project. The core creates the envelope, hashes the validated command with operator and request identity, appends an event, catches projections up, and returns the committed event ID and revision. A caller can supply an admission check for the M2.7 context policy. M2.9 will map service errors to HTTP responses.

`engagement.updated` patches replace named metadata fields and collections. Omitted fields retain their values; nullable fields can be cleared. Scope changes use `scope.object-added` for inclusion, `scope.excluded` for exclusion, `scope.object-updated` for correction, `scope.object-removed` for removal, and `scope.object-reclassified` to move an ID between sides. Correction preserves ID and kind. Reclassification preserves the ID and records a single event. A scope snapshot is accepted at creation only. A transferred project's prior local operator ID remains in its history and view until `roster.reassign` writes an explicit roster update, changing the selected member to the installation operator and making the former local member external.

A repeated operation ID with the same command returns its original result before checking the current revision. Reuse for a different command conflicts; an overlapping attempt reports `operation_in_progress`. Changed operations are recovered from the portable ledger. No-change outcomes live only in the installation registry and are excluded from project exports. If append commits and projection catch-up fails, the service reports `projection_repair_required` with the committed event ID and revision. A retry or explicit rebuild catches up without appending again. A failed append leaves the operation ID available for retry. Project creation remains the staged M2.3 storage operation because it publishes a new directory and registry entry; its creation event is replayed by the same projections.
