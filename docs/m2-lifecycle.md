# M2.6 lifecycle policy

The persisted lifecycle has six states: Draft, Lab, Active, Paused, Closing, and Closed. `kind` stays `engagement` or `lab` for the entire project history. Blackout is a later effective restriction calculated from RoE and time windows; it is never written as a lifecycle state. Manual pause and every M2.6 transition are available without documents, reports, cleanup records, a RoE, or a testing window.

The pure transition policy implements the [M2.1 matrix](m2-core-contract.md#persisted-state-transition-matrix). Pausing saves the current state in `resume_state`; beginning Closing saves the underlying Draft/Lab/Active state in `closing_origin`. A pause of Closing keeps that origin. Cancellation returns to the origin and clears both saved fields, even when the closing episode began from a paused state. Closed can reopen to Active for engagements or Lab for labs. Repeated activate in Active, pause in Paused, begin_closing in Closing, and close in Closed are successful no-ops with no engagement event.

The mutation service writes changed transitions as `engagement.state-changed` version-1 events. The event stores the command, trimmed reason, previous and next lifecycle snapshots, operation ID, and command hash; its envelope is attributed and timed by the core. Retries, stale revision checks, serialized writes, projection recovery, and no-op persistence use the M2.5 path. A read-only service query returns all seven commands with an allowed flag and an explanation for invalid commands. Replay applies the same policy and refuses a recorded command or next snapshot that contradicts the previous state.

The policy exposes future execution posture: Draft/Lab/Active permit runner admission, Paused stops admission, Closed disables the runner, and Closing warns for new persistence or destructive classes. M4/M5 implement actual runner and RoE enforcement. Future close integration has runner quiescence and M8/M9 cleanup/report status hooks; none are active prerequisites in M2. Closing does not sign a ledger checkpoint. Closed project content requires an audited reopen before metadata, scope, or roster changes.
